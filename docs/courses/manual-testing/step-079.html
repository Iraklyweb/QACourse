Лекция «Вложенность и уровни в JSON»

 

Что это такое

Вложенность — это когда объект или массив в JSON содержит внутри себя другие объекты или массивы. Каждый уровень вложенности — это ещё один шаг внутрь структуры.

Сид (от англ. seed) — это предустановленные или сгенерированные данные, которые автоматически добавляются в систему для тестирования или разработки. Это специальный скрипт, который заполняет базу данных информацией согласно заданному шаблону. Он может вызываться как автоматически так и руками. Где-то вообще не используется генерация данных и делается это вручную. В каждой компании всё по-разному. Вам сообщат как это сделать или нет, если вы не любознательны.

Пример:

{

  "user": {

    "address": {

      "city": "Москва"

    }

  }

}

 

Здесь:

— уровень 0: корневой JSON
— уровень 1: user
— уровень 2: address
— уровень 3: city

Такая вложенность позволяет описывать сложные иерархические данные, не расплющивая всё в длинные названия.

 

Откуда появляется вложенность

Вложенность не появляется случайно. Её закладывают на этапе проектирования API — этим занимается аналитик или разработчик, ориентируясь на поставленную задачу.

Например, задача: нужно вернуть информацию о пользователе с адресом и списком заказов.

Аналитик оформляет описание задачи в виде таблицы, в которой фиксируется структура, типы и уровень вложенности каждого поля:

Это — требования к структуре. На основе этой таблицы:

— разработчик реализует JSON-ответ
— тестировщик сверяет фактический JSON с этой схемой

Вложенность, названия и типы — это всё ожидаемое поведение. Именно по этим путям тестировщик и будет проверять: что пришло, где лежит, и соответствует ли заявленной структуре.

 

Зачем нужна вложенность

Вложенность используется для того, чтобы логически группировать связанные между собой данные. Она избавляет от плоских и нечитаемых конструкций, в которых всё сведено к длинным ключам с префиксами.

Вместо такого варианта:

{

  "user_name": "Иван",

  "user_address_city": "Москва",

  "user_order_0_id": 1001

}

 

используется вложенная структура:

{

  "user": {

    "name": "Иван",

    "address": {

      "city": "Москва",
      "street": "Строителей"

    },

    "orders": [

      {

        "id": 1001,

        "total": 2500

      },

      {

        "id": 1002,

        "total": 3500

      }

    ]

  }

}

 

Преимущества вложенности:

— Связанные данные находятся рядом
— Структура читается и визуально отражает логику предметной области
— Упрощается масштабирование: можно добавлять поля без конфликтов и повторов
— Удобно работать с массивами объектов
— Формируются иерархии, которые можно обрабатывать на уровне кода, схем, документации

Вложенность — это способ сделать данные чистыми, логичными и удобными для всех, кто с ними работает: от разработчиков до автоматических систем.

 

Что делает тестировщик

Тестировщик сверяет JSON-ответ с таблицей, которую составил аналитик. Проверка идёт поэтапно:

1. Структура и вложенность

Проверяется, что поля находятся строго на своих местах. Если в таблице путь user.address.city, а в json поле city пришло вне address, это уже нарушение вложенности.

Отклонением считается:

— поле пришло выше или глубже ожидаемого уровня
— вложенность нарушена (например, массив orders внутри address, а не user)
— пропущен промежуточный объект (user.departmentCode вместо user.department.code)
— поле вообще отсутствует

Сверка ведётся визуально или с помощью автотестов. 

Один раз проверили и хватит, пока не внесли глобальные изменения нечего второй раз проверять.

 

2. Типы данных

Даже если путь верный, важно, чтобы тип значения совпадал с ожиданиями.

Типовые ошибки:

— число приходит как строка ("1001" вместо 1001)
— массив как строка ("")
— объект как null без пояснений в требованиях

Сравниваются только фактические типы и то, что указано в таблице. Всё, что не совпадает — отдельная точка разбора.

Один раз проверили и хватит, пока не внесли глобальные изменения нечего второй раз проверять.

 

3. Значения (проверяются только при контексте)

Значения никогда не проверяются “просто на глаз”. На тестовом стенде никто не даст гарантию, что данные настоящие. Пример из реальности:

{

  "user": {

    "name": "123234",

    "address": {

      "city": "ываыва"

    }

  }

}

 

На вопрос “это баг?” — нельзя ответить. Ты вводил значения – проверяешь и анализируешь на правильность расположения значений в ключах, если нет – значит, значение игнорируется и не проверяются.

Проверять значения имеет смысл только если:

— ты сам их ввёл перед этим (в UI, через POST-запрос, напрямую в БД)
— ты точно знаешь, какое значение должно быть и почему
— ты проверяешь цепочку действий и контролируешь все шаги

Как подготавливать значения, чтобы их потом можно было проверить

Если ты создаёшь данные вручную — нужно сразу подставлять такие значения, чтобы потом безошибочно узнать их в ответе. При этом:

1. Не используй слово “test” НИКОГДА.

Если поле name содержит "test", ты никогда не поймёшь, это твой ввод или сид. "test" встречается повсюду: в заглушках, в сидовых данных, в старых кейсах и в десятки других полях. Это мусор.
2. Используй название поля + цифру.

Если ты заполняешь поле city, впиши "city47".
Если это comment, впиши "comment003".
Так ты точно поймёшь, что это значение из нужного поля, и что оно твоё.

Работает только с типом данных “строка”.

3. Не дублируй значения между полями.

Если во всех полях будет "abc123", ты не узнаешь, откуда что пришло. "name": "abc123" и "city": "abc123" — и что теперь? Где что?

4. Используй уникальность.

Если все значения уникальны, ты всегда можешь точно отследить: это поле отработало как надо, или система перепутала структуру.

 

Вывод:

Если не ты указал значения — значения не проверяешь. Если ты указал — создавай их так, чтобы безошибочно узнать своё. Иначе потратишь время на баг, которого не было, и сам же не сможешь доказать, что был прав.

Что делать при расхождениях

Если структура или вложенность отличаются от описания в требованиях — не нужно сразу писать баг репорт.

Алгоритм действий:

  1. Сравнить полученный JSON с таблицей из требований
     

  2. Зафиксировать расхождение (в голове/на электронном носителе): отсутствует путь, не тот тип, не та вложенность
     

  3. Уточнить у разработчика: реализовано так специально или ошибка
     

  4. Уточнить у аналитика: а как должно быть по логике бизнеса
     

  5. Получить согласованную точку правды
     

  6. Если реализация действительно не соответствует — создаётся баг репорт
     

  7. Если реализация корректна, а ошибка в требованиях — обновляется документация аналитиком
     

Итог

Вложенность — это основа структуры JSON. Она задаётся аналитиком в виде путей и реализуется разработчиком. Тестировщик сверяет вложенность, названия и типы. Значения проверяются только при наличии контекста. Большинство значений в API-ответах — случайные или заглушечные, и воспринимать их как баги без подтверждения нельзя. Любое расхождение между фактом и требованиями — это точка уточнения, а не автоматический дефект.
