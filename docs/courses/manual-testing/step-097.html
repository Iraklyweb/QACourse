Лекция «Метод PUT: как работает и зачем нужен»

 

Метод PUT используется для полного обновления ресурса или его создания, если он ещё не существует. В отличие от POST, который добавляет новые данные, PUT заменяет существующие.

Если сравнивать с реальной жизнью, PUT — это как редактирование профиля: вы отправляете обновлённые данные, и сервер полностью заменяет старые значения новыми.

 

Как работает PUT?

Метод PUT применяется, когда клиенту необходимо обновить существующий ресурс или создать его, если он отсутствует. Данные передаются в теле запроса, а сам запрос отправляется по конкретному URL, который идентифицирует изменяемый ресурс.

1. Клиент отправляет запрос:

Клиент формирует PUT-запрос с полным набором данных, которые должны заменить текущий ресурс.

Пример запроса:

PUT /users/1 HTTP/1.1  

Host: api.example.com  

Content-Type: application/json  

{

  "id": 1,

  "name": "Alice",

  "email": "alice@example.com",

  "role": "admin"

}

→ Отправляются все поля, даже если изменяется только одно.

2. Сервер обрабатывает запрос:

  • Проверяет, существует ли ресурс с таким ID.

  • Если ресурс существует → обновляет данные (перезаписывает всю сущность).

  • Если ресурс не существует → создаёт новый (если API это поддерживает).

3. Сервер отправляет ответ:

  • 200 OK, если обновление прошло успешно.

  • 201 Created, если ресурс был создан (PUT иногда используется для этого).

  • 400 Bad Request, если не хватает данных.

  • 404 Not Found, если ресурс отсутствует и API не поддерживает его создание.

Пример ответа:

HTTP/1.1 200 OK  

Content-Type: application/json  

{

  "id": 1,

  "name": "Alice",

  "email": "alice@example.com",

  "role": "admin"

}

PUT-запрос всегда заменяет весь объект, даже если изменилось только одно поле. Если нужно частично обновить данные, используется PATCH.

 

Что будет, если не указать все поля?

Так как PUT заменяет весь ресурс, если отправить запрос без некоторых полей, сервер может удалить отсутствующие данные или вернуть ошибку.

1. Исходный ресурс в базе:

{

  "id": 1,

  "name": "Alice",

  "email": "alice@example.com",

  "role": "admin"

}

2. Клиент отправляет PUT-запрос, забыв указать поле role:

PUT /users/1 HTTP/1.1  

Host: api.example.com  

Content-Type: application/json  

{

  "id": 1,

  "name": "Alice",

  "email": "alice@example.com"

}

3. Что может сделать сервер?

Если сервер перезаписывает ресурс, поле role будет удалено. Новый ресурс в базе:

{

  "id": 1,

  "name": "Alice",

  "email": "alice@example.com"

}

Поле "role" исчезло.

Если сервер требует полный набор данных, он может вернуть 400 Bad Request с сообщением об ошибке:

HTTP/1.1 400 Bad Request  

Content-Type: application/json  

{

  "error": "Missing required field: role"

}

 

Основные свойства метода PUT

Метод PUT предназначен для полного обновления ресурса. Он имеет несколько ключевых особенностей, которые отличающих его от других методов.

PUT является идемпотентным

  • Повторный запрос с одинаковыми данными не создаст новых ресурсов, а просто перезапишет существующие.

  • Если отправить один и тот же PUT-запрос несколько раз, состояние ресурса не изменится после первого успешного выполнения.

Влияние на безопасность и состояние сервера

  • PUT изменяет состояние сервера, так как заменяет существующий ресурс. Тем самым PUT небезопасен с точки зрения изменения данных на сервере.

  • Безопасен с точки зрения передачи данных, так как они передаются в теле запроса, а тело в свою очередь шифруется.

  • В отличие от PATCH, который обновляет отдельные поля, PUT требует полного набора данных, что может привести к потере информации, если какие-то поля не переданы.

  • Без HTTPS данные остаются незащищёнными и могут быть перехвачены.

  • PUT скрывает данные от истории браузера и логов URL, но передаваемая информация остаётся уязвимой, если не используется шифрование на уровне соединения (TLS/HTTPS).

  • Как и другие методы изменения данных, PUT требует авторизации, если ресурс защищён.

Передача данных

  • PUT передаёт весь объект целиком, даже если изменяется только одно поле.

  • Это делает запросы более ресурсоёмкими, особенно при работе с большими объектами.

Ограничения длины URL отсутствуют

  • Данные передаются в теле запроса, а не через URL, поэтому PUT не ограничен по размеру данных.

  • Однако некоторые API могут накладывать свои лимиты на размер тела запроса.

Форматы данных

  • Чаще всего используется JSON, так как REST API обычно работают с этим форматом.

  • Однако PUT может поддерживать XML, файлы или другие форматы, в зависимости от API.

Кэширование

  • PUT не кэшируется браузерами и прокси-серверами, так как он изменяет данные.

  • Однако сервер может использовать заголовки ETag и Last-Modified, чтобы проверять актуальность данных перед обновлением.

 

Дополнительные особенности метода PUT

PUT заменяет весь объект

  • В теле запроса передаются все поля, даже если изменяется только одно.

  • В отличие от PATCH, который обновляет только переданные поля, PUT требует полный объект.

PUT требует существования ресурса

  • Если объект существует, PUT заменяет его.

  • Если объекта не существует, PUT создает его. По логике с POST.

  • Если объект не найден, сервер может вернуть 404 Not Found, если API не поддерживает создание ресурса через PUT.

PUT работает на уровне конкретного ресурса

  • PUT-запрос всегда выполняется для конкретного объекта (/users/1).

  • В отличие от POST, который может работать с коллекциями (/users).

PUT удобен, когда нужно обновить весь ресурс

  • Если нужно заменить все данные, PUT — подходящий метод.

  • Если же требуется изменить только часть информации, используется PATCH.

 

Итог

Метод PUT используется для полного обновления ресурса. Если отправить PUT-запрос, сервер перезапишет всю сущность, даже если изменилось только одно поле.

 

Как тестируют PUT?

  • Если есть доступ к БД, проверяют, обновились ли все данные.

  • Если доступа к БД нет, делают GET-запрос, чтобы убедиться, что изменения применились.

  • Проверяют, возвращает ли сервер корректный статус-код (200 OK при обновлении, 201 Created, если ресурс создаётся, 400 Bad Request при ошибке).

  • Тестируют обработку неполных данных (что делает сервер, если не передать все поля).

PUT чаще всего используется для замены существующих данных, но в некоторых API его применяют и для создания ресурса, если он отсутствует. Если нужно изменить только одно поле, вместо PUT лучше использовать PATCH.
