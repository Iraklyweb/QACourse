Лекция «Кэширование: серверное и клиентское»

 

Кэширование — это механизм, который позволяет временно сохранять данные, чтобы ускорить доступ к ним при повторных запросах. Оно делится на две основные категории: серверное и клиентское. Для тестировщика нужно понимать разницу между ними и при получении данных задач, уточнить, что имеется в виду и как лучше это сделать у вас на проекте.

 

Серверное кэширование

Серверное кэширование используется для уменьшения нагрузки на сервер и ускорения обработки запросов. Сервер сохраняет обработанные данные и отправляет их клиенту при повторных запросах, вместо того чтобы генерировать их заново.

Пример: Вы запрашиваете список продуктов. Сервер сохраняет результат в кэше, чтобы не обращаться к базе данных при каждом запросе.

Основные характеристики:

  • Где хранится: На сервере или промежуточных уровнях (например, прокси-серверах, CDN).

  • Когда используется: Для ресурсоёмких запросов, результаты которых редко меняются.

  • Примеры инструментов: Redis, Memcached.

 

Клиентское кэширование

Клиентское кэширование используется для уменьшения количества запросов к серверу. Клиент (обычно браузер или приложение) сохраняет данные локально и использует их, если ресурс не изменился.

Пример: Браузер сохраняет список товаров локально. При повторном запросе сервер отвечает 304 Not Modified — браузер использует кэшированные данные.

Основные характеристики:

  • Где хранится: В памяти клиента (например, браузера).

  • Когда используется: Для ускорения работы и снижения нагрузки на сеть.

  • Инструменты: В браузере можно проверить кэш через вкладку Application или Network в DevTools.

 

Как проверить кэширование?

Клиентское кэширование

Нужно уметь очищать кэш.

  1. Откройте DevTools в браузере:

    • Вкладка Network — чтобы увидеть заголовки запросов и ответов.

    • Вкладка Application — для просмотра сохранённых кэшированных данных (например, Local Storage, Session Storage, Cache Storage).

  2. Отправьте запрос к ресурсу и проверьте заголовки:

    • Cache-Control: Указывает правила кэширования.

    • ETag: Позволяет серверу сравнить версии ресурсов.

    • If-Modified-Since: Заголовок запроса, который проверяет, изменился ли ресурс

    • If-None-Match: Заголовок запроса, который используется для проверки, изменилась ли версия ресурса. Клиент отправляет сохранённое значение ETag, и если оно совпадает с текущей версией на сервере, сервер отвечает 304 Not Modified, указывая, что можно использовать закэшированные данные, вместо повторной загрузки ресурса..

Пример для GET-запроса с клиентским кэшем:

GET /products HTTP/1.1

Host: example.com

If-Modified-Since: Wed, 24 Jan 2025 10:00:00 GMT

If-None-Match: "v1.0"

Ответ:

304 Not Modified

Браузер использует кэшированные данные.

 

Серверное кэширование 

Для общего развития. Погружаться как с этим работать не надо.

  1. Проверьте, где именно кэшируются данные:

    • На сервере приложений (например, Redis).

    • На уровне прокси или CDN (например, Cloudflare).

  2. Используйте инструменты мониторинга:

    • Смотрите, был ли запрос обработан сервером или возвращён из кэша.

Пример проверки серверного кэша: Если запрос обработан из кэша, сервер может вернуть заголовок:

X-Cache: HIT

Если данные не кэшированы:

X-Cache: MISS

Проблемы, связанные с кэшированием

  1. Устаревшие данные: Если кэш не обновляется вовремя, пользователи могут видеть устаревшую информацию.

  2. Конфликт серверного и клиентского кэша: Иногда сервер возвращает обновлённые данные, но клиент продолжает использовать старую версию из локального кэша.

  3. Трудности тестирования: Тестировщику нужно учитывать настройки кэша на разных уровнях (сервер, прокси, клиент).

 

Что важно знать для тестирования?

  1. Для клиентского кэширования:

    • Проверяйте заголовки, связанные с кэшированием (например, Cache-Control, ETag).

    • Убедитесь, что клиент получает 304 Not Modified вместо полного ответа при использовании кэша.

  2. Для серверного кэширования:

    • Проверяйте, откуда поступают данные (HIT или MISS).

    • Убедитесь, что кэш обновляется при изменении данных.

  3. Работа с инструментами: Используйте вкладки Application и Network в DevTools для проверки клиентского кэша.

 

Итог

В большинстве случаев вы будете работать только с клиентским кэшем, и ваша основная задача будет заключаться в его очистке. Проверять клиентский кэш придётся редко, только по прямому запросу или в рамках специфических требований. Без чёткой необходимости или указаний влезать в кэширование не имеет смысла.

Однако, когда кэширование становится частью вашей работы, основные задачи будут такими:

  1. Очистка кэша: Убедитесь, что данные обновлены и система работает корректно.

  2. Проверка заголовков и поведения: Проводится редко, но важно проверить логику обновления кэша, если это прописано в требованиях.

  3. Избегание лишнего вмешательства: Не трогайте кэширование, если это не предусмотрено задачей, чтобы не создать ненужных проблем.

Такой подход позволит эффективно работать с кэшированием и не тратить время на лишние действия.
