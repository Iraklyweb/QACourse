Подведём итоги изучения HTTP-методов. Здесь мы напомним ключевые понятия, сравним методы в таблице и свяжем всё воедино.

 

Что такое идемпотентность?

Идемпотентность — это свойство метода, при котором повторный запрос с теми же данными не приводит к дополнительным изменениям состояния на сервере. Это означает, что после первого запроса ресурс на сервере не изменяется, даже если запрос выполнен повторно.

  • Пример:

    • Метод GET: если вы запрашиваете список отзывов, повторные запросы возвращают одни и те же данные (если серверные данные не изменились).

    • Метод DELETE: первый запрос удаляет ресурс, а последующие запросы просто подтверждают, что ресурса больше нет.

Идемпотентные методы:

  • GET, PUT, DELETE, HEAD, OPTIONS Эти методы, даже при повторных запросах, не приводят к дополнительным изменениям на сервере.

Неидемпотентные методы:

  • POST, PATCH

    • POST: Обычно создаёт новые ресурсы. Повторный запрос может создать дубликаты.

    • PATCH: В теории считается неидемпотентным, так как его поведение зависит от реализации. Однако, если сервер реализует PATCH как идемпотентный (например, заменяя поле определённым значением), он тоже может быть идемпотентным.

Исключения:

  • POST при поисковых запросах: Например, если POST используется для фильтрации товаров, повторный запрос не изменяет данные, а возвращает одинаковые результаты.

  • PATCH с предопределёнными значениями: Если PATCH заменяет поле одним и тем же значением, его можно считать идемпотентным.

 

Безопасные и небезопасные методы

HTTP-методы можно разделить на безопасные и небезопасные в зависимости от того, изменяют ли они состояние на сервере.

Безопасные методы

Безопасные методы не изменяют данные на сервере. Они используются только для получения информации.

  • Методы: GET, HEAD, OPTIONS.

  • Пример:

    • GET /users/1: запрос возвращает информацию о пользователе, но не вносит изменений в данные.

Небезопасные методы

Небезопасные методы изменяют состояние на сервере.

  • Методы: POST, PUT, PATCH, DELETE.

  • Пример:

    • POST /users: создаёт нового пользователя.

    • DELETE /users/1: удаляет пользователя.

 

HTTP-методы — рекомендации, а не правила

HTTP-методы описывают рекомендованный подход, но это не строгие ограничения. Реализация методов может отличаться в зависимости от API.

  • Пример:

    • Сервер может использовать POST для создания и обновления данных, хотя для обновления лучше подошли бы PUT или PATCH.

    • Или же метод DELETE может быть реализован как логическое удаление, при котором данные остаются в базе, но отмечаются как "удалённые".

Важно понимать, что разработчики могут отойти от стандартов и реализовать методы так, как считают нужным.

Пример: управление отзывами в интернет-магазине

Чтобы понять, как методы связаны между собой, рассмотрим процесс управления отзывами в интернет-магазине:

  1. Получение отзывов (GET): Клиент хочет увидеть все отзывы о товаре.

    • Пример: "Покажи отзывы о смартфоне Xiaomi."

    • Сервер возвращает список отзывов.

  2. Добавление отзыва (POST): Клиент пишет новый отзыв о товаре.

    • Пример: "Я хочу оставить отзыв о смартфоне."

    • Сервер сохраняет отзыв в пербазе данных.

  3. Обновление отзыва (PATCH): Клиент хочет изменить текст своего отзыва.

    • Пример: "Исправь мой отзыв: добавь, что камера хорошая."

    • Сервер обновляет только текст отзыва.

  4. Удаление отзыва (DELETE): Клиент решает удалить свой отзыв.

    • Пример: "Я хочу удалить свой отзыв."

    • Сервер удаляет отзыв из базы данных.

 

Итог

HTTP-методы — основа работы с API. В реальной работе тестировщик чаще всего сталкивается с GET, POST, PUT, PATCH и DELETE.

Вы будете ориентироваться на требования, чтобы корректно проверить API. Без требований тестирование превращается в угадайку, где непонятно:

  • Какие поля обязательные?

  • Где границы допустимых значений?

  • Как должен выглядеть корректный результат?

Если требований нет, общайтесь с разработчиками. Они могут объяснить, какие валидации настроены, какие поля обязательны и какой результат ожидается.

В конечном итоге главное не метод, а логика его работы. Без понимания, что должно происходить, любые проверки API превращаются в формальность.
