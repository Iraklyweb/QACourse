Лекция «Метод PATCH: как работает и зачем нужен»

 

Метод PATCH используется для частичного обновления ресурса. В отличие от PUT, который заменяет всю сущность, PATCH позволяет изменить только отдельные поля, не затрагивая другие данные.

Если сравнивать с реальной жизнью, PATCH — это как изменение адреса доставки в заказе: вы обновляете только поле address, а остальные данные (товары, способ оплаты) остаются без изменений.

 

Как работает PATCH?

Метод PATCH позволяет изменить только часть данных, не затрагивая весь ресурс. В отличие от PUT, он обновляет только переданные поля, оставляя остальные без изменений.

1. Исходный ресурс в базе:

{

  "id": 1,

  "name": "Alice",

  "email": "alice@example.com",

  "role": "admin"

}

2. Клиент отправляет PATCH-запрос с изменённым email:

PATCH /users/1 HTTP/1.1  

Host: api.example.com  

Content-Type: application/json  

{

  "email": "new.email@example.com"

}

→ Передаётся только поле email, остальные данные остаются без изменений.

3. Сервер обрабатывает запрос:

  • Проверяет, существует ли ресурс (/users/1).

  • Обновляет только указанные поля, не затрагивая name и role.

  • Записывает изменения в базу данных.

4. Обновлённый ресурс после PATCH:

{

  "id": 1,

  "name": "Alice",

  "email": "new.email@example.com",

  "role": "admin"

}

→ Email изменился, но name и role остались неизменными.

5. Сервер отправляет ответ:

  • 200 OK, если обновление прошло успешно, и сервер возвращает обновлённые данные.

  • 204 No Content, если сервер обновил данные, но не возвращает тело ответа.

  • 400 Bad Request, если запрос составлен некорректно.

  • 404 Not Found, если ресурс отсутствует.

PATCH удобен, когда нужно изменить только отдельные поля, а PUT был бы избыточен.

 

Основные свойства метода PATCH

PATCH не является идемпотентным

  • Повторный запрос с одинаковыми данными может привести к разным результатам, если сервер выполняет дополнительные операции (например, обновляет дату изменения).

  • Однако в большинстве случаев PATCH-операция просто обновляет указанные поля, не изменяя остальную сущность.

  • Почему PATCH не является идемпотентным — неизвестно, так как в его логике нет явных причин для этого.

Влияние на безопасность и состояние сервера

  • PATCH изменяет состояние сервера, так как заменяет существующий ресурс. Тем самым PATCH небезопасен с точки зрения изменения данных на сервере.

  • Безопасен с точки зрения передачи данных, так как они передаются в теле запроса, а тело в свою очередь шифруется.

  • В отличие от PUT, который требует полный объект, PATCH позволяет внести изменения частично, что снижает риск потери данных.

  • Без HTTPS данные остаются незащищёнными и могут быть перехвачены.

  • PATCH скрывает данные от истории браузера и логов URL, но передаваемая информация остаётся уязвимой, если не используется шифрование на уровне соединения (TLS/HTTPS).

  • Как и другие методы изменения данных, PATCH требует авторизации, если ресурс защищён.

Передача данных

  • PATCH передаёт только изменяемые поля, а не весь объект, как PUT.

  • Это делает запросы компактнее и быстрее, особенно при обновлении больших объектов.

Ограничения длины URL отсутствуют

  • Данные передаются в теле запроса, а не через URL, поэтому PATCH не ограничен по размеру данных.

  • Однако некоторые API могут накладывать свои лимиты на размер тела запроса.

Форматы данных

  • Чаще всего используется JSON, так как REST API обычно работают с этим форматом.

  • Однако PATCH может поддерживать XML, файлы или другие форматы, в зависимости от API.

Кэширование

  • PATCH не кэшируется браузерами и прокси-серверами, так как он изменяет данные.

  • Однако сервер может использовать заголовки ETag и Last-Modified, чтобы проверять актуальность данных перед обновлением.

 

Дополнительные особенности метода PATCH

PATCH обновляет только указанные поля

  • В теле запроса передаются только те данные, которые должны измениться.

  • Остальные поля остаются без изменений, в отличие от PUT, который требует полный объект.

PATCH требует существования ресурса

  • Если объект существует, PATCH обновляет его поля.

  • Если объект не найден, сервер обычно возвращает 404 Not Found, так как PATCH не создаёт новый ресурс, в отличие от PUT.

PATCH работает на уровне конкретного ресурса

  • PATCH-запрос всегда выполняется для конкретного объекта (/users/1).

  • В отличие от POST, который может работать с коллекциями (/users).

PATCH удобен, когда нужно изменить только часть данных

  • Если требуется обновить весь объект, используется PUT.

  • Если нужно изменить только отдельные поля, PATCH — лучший вариант.

 

Итог

Метод PATCH используется для частичного обновления ресурса, позволяя изменить только переданные поля, не затрагивая остальные. В отличие от PUT, который заменяет всю сущность, PATCH делает запросы компактнее и быстрее.

 

Как тестируют PATCH?

  • Если есть доступ к БД, проверяют, обновились ли только переданные поля, а остальные остались неизменными.

  • Если доступа к БД нет, делают GET-запрос до и после PATCH, сравнивая изменения.

  • Проверяют, возвращает ли сервер корректные статус-коды (200 OK, 204 No Content, 400 Bad Request).

  • Тестируют обработку некорректных данных (например, если передать пустой объект).

PATCH удобен в случаях, когда PUT был бы избыточен. Однако, если API требует полного набора данных для обновления, нужно использовать PUT вместо PATCH.
