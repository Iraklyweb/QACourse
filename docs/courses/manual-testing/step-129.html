Лекция «Клиентские проблемы»

Лекция «Клиентские проблемы»

 

1. Кнопка "не кнопка"

Проблема: Элемент визуально выглядит как кнопка, но в коде это может быть <div> или <span> без привязанного функционала (onclick или других событий).

Пример: HTML:

<div class="button">Отправить</div>

Вместо этого должно быть:

<button onclick="submitForm()">Отправить</button>

Как проверить:

  1. Откройте DevTools → вкладка Elements, найдите элемент кнопки в DOM-дереве.

  2. Убедитесь, что это настоящий элемент кнопки (<button> или <input type="button">).

  3. Проверьте вкладку Event Listeners, чтобы убедиться, что к кнопке привязан обработчик события.

Последствия:

  • Нажатие не вызывает действий.

  • Запрос к серверу не отправляется.

Возможные статус-коды:

  • Нет, так как запрос не отправляется.

 

2. Кнопка задизейблена (неактивна/невозможно взаимодействовать)

Проблема: Кнопка отключена (задизейблена disabled), из-за чего пользователь не может её нажать.

Пример: HTML:

<button disabled>Отправить</button>

Как проверить:

  1. Откройте DevTools → вкладка Elements.

  2. Проверьте, есть ли у кнопки атрибут disabled.

  3. Удалите disabled и проверьте, срабатывает ли кнопка после этого.

Последствия:

  • Запрос к серверу не отправляется.

Возможные статус-коды:

  • Нет, так как запрос не отправляется.

 

3. Нарушен путь к кнопке в HTML

Проблема: Кнопка может быть неправильно встроена в структуру DOM, из-за чего обработчик события или привязка к логике не работают.

Пример:

  • Изначально логика привязана к:

<button id="submit">Отправить</button>

  • После рефакторинга кнопка переместилась или изменила ID:

<button id="send">Отправить</button>

Как проверить:

  1. Проверьте DOM-структуру в DevTools → вкладка Elements.

  2. Убедитесь, что кнопка находится в правильном месте относительно других элементов.

  3. Проверьте, подключены ли связанные события или логика работы кнопки.

Последствия:

  • Нажатие не вызывает действий.

  • Запрос к серверу не отправляется.

Возможные статус-коды:

  • Нет, так как запрос не отправляется.

 

4. Неправильный URL или эндпоинт

Проблема: Кнопка отправляет запрос на неправильный URL.

Пример запроса: Клиент отправляет:

POST /api/wrong-endpoint HTTP/1.1

Host: example.com

Content-Type: application/json

Ожидается:

POST /api/correct-endpoint HTTP/1.1

Host: example.com

Content-Type: application/json

Как проверить:

  1. Проверьте логи запросов в DevTools → вкладка Network.

  2. Убедитесь, что URL соответствует документации API.

Последствия:

  • Сервер возвращает ошибку 404 Not Found.

Возможные статус-коды:

  • 404 Not Found — ресурс не найден.

  • 400 Bad Request, если URL содержит некорректные параметры.

 

5. Пустое тело запроса

Проблема: Кнопка отправляет запрос, но без данных в теле.

Пример запроса: Клиент отправляет:

POST /api/submit HTTP/1.1

Host: example.com

Content-Type: application/json

{}

Ожидается:

POST /api/submit HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "name": "John Doe",

    "email": "john.doe@example.com"

}

Как проверить:

  1. Откройте DevTools → вкладка Network, проверьте тело отправленного запроса.

  2. Сравните с ожидаемой структурой запроса, указанной в документации.

Последствия:

  • Сервер отклоняет запрос, возвращая ошибку.

Возможные статус-коды:

  • 400 Bad Request, если сервер ожидает данные.

  • 500 Internal Server Error, если сервер не обрабатывает пустое тело корректно.

 

6. 401 Unauthorized

Проблема: Клиент отправляет запрос, но сервер требует аутентификации.

Пример запроса: Клиент отправляет:

GET /api/secure-resource HTTP/1.1

Host: example.com

Ожидается:

GET /api/secure-resource HTTP/1.1

Host: example.com

Authorization: Bearer valid_token

Как проверить:

  1. Проверьте наличие заголовка Authorization в запросе.

  2. Убедитесь, что токен авторизации корректен и не истёк.

Последствия:

  • Сервер отклоняет запрос, возвращая ошибку 401 Unauthorized.

Возможные статус-коды:

  • 401 Unauthorized.

 

7. 403 Forbidden

Проблема: Клиент аутентифицирован, но не имеет прав на выполнение операции.

Пример запроса: Клиент отправляет:

POST /api/admin-action HTTP/1.1

Host: example.com

Authorization: Bearer valid_user_token

Ожидается:

POST /api/admin-action HTTP/1.1

Host: example.com

Authorization: Bearer admin_token

Как проверить:

  1. Убедитесь, что роль пользователя соответствует уровню доступа к ресурсу.

  2. Проверьте права доступа для запрашиваемого эндпоинта.

Последствия:

  • Сервер отклоняет запрос, возвращая ошибку 403 Forbidden.

Возможные статус-коды:

  • 403 Forbidden.

 

8. Некорректные данные в запросе

Проблема: Кнопка отправляет запрос с неверными параметрами или значениями (например, атрибуты не соответствуют требованиям).

Пример запроса: Клиент отправляет:

POST /api/submit HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "name": "John Doe",

    "email": "not-an-email"

}

Ожидается:

POST /api/submit HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "name": "John Doe",

    "email": "john.doe@example.com"

}

Как проверить:

  1. Проверьте параметры запроса в DevTools → вкладка Network.

  2. Сравните с требованиями API.

Последствия:

  • Сервер возвращает ошибку валидации.

Возможные статус-коды:

  • 400 Bad Request.

  • 422 Unprocessable Entity.

 

9. Чувствительность к регистру

Проблема: Значения параметров или атрибутов зависят от регистра. Например, сервер ожидает Active, но клиент отправляет active.

Пример запроса: Клиент отправляет:

POST /api/user-status HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "status": "active"

}

Ожидается:

POST /api/user-status HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "status": "Active"

}

Как проверить:

  1. Убедитесь, что регистр параметров совпадает с требованиями API.

  2. Попробуйте разные варианты регистра для значений атрибутов.

Возможные статус-коды:

  • 400 Bad Request.

  • 422 Unprocessable Entity.

 

10. Проблемы с обработкой ответа на фронте

Проблема: Фронтенд не может обработать данные, возвращённые сервером. Например, сервер вернул данные в неожиданном формате.

Пример ответа: Сервер возвращает:

{

    "user": {

        "name": "John Doe"

    }

}

Ожидается:

{

    "username": "John Doe"

}

Как проверить:

  1. Проверьте формат возвращаемых данных через DevTools → вкладка Network.

  2. Убедитесь, что фронтенд обрабатывает возвращённые данные корректно.

Последствия:

  • Интерфейс приложения не отображает или неправильно отображает данные.

Возможные статус-коды:

  • 200 OK, но данные не отображаются.

 

11. Некорректное значение атрибута

Проблема: Клиент передаёт значение, которое не соответствует ожидаемому.

Пример запроса: Клиент отправляет:

POST /api/product HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "price": "ten dollars"

}

Ожидается:

POST /api/product HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "price": 10.00

}

Как проверить:

  1. Сравните передаваемые значения с требованиями документации API.

  2. Используйте DevTools → вкладка Network, чтобы проверить тело запроса.

Возможные статус-коды:

  • 400 Bad Request.

  • 422 Unprocessable Entity.

 

12. Отсутствие значения у атрибута

Проблема: Значение атрибута отсутствует, хотя оно обязательно.

Пример запроса: Клиент отправляет:

POST /api/product HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "name": "Laptop",

    "price": ""

}

Ожидается:

POST /api/product HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "name": "Laptop",

    "price": 1000.00

}

Как проверить:

  1. Убедитесь, что все обязательные поля заполнены.

  2. Проверьте структуру запроса через DevTools → вкладка Network.

Возможные статус-коды:

  • 400 Bad Request.

  • 422 Unprocessable Entity.

 

13. Тип значения не соответствует ожидаемому

Проблема: Тип данных атрибута неверен.

Пример запроса: Клиент отправляет:

POST /api/user HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "age": "twenty"

}

Ожидается:

POST /api/user HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "age": 20

}

Как проверить:

  1. Убедитесь, что тип данных совпадает с требованиями API.

  2. Отправьте запрос через Postman или DevTools.

Возможные статус-коды:

  • 400 Bad Request.

  • 422 Unprocessable Entity.

 

14. Некорректный формат значения

Проблема: Значение соответствует типу, но его формат некорректен.

Пример запроса: Клиент отправляет:

POST /api/user HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "birthdate": "31-12-1990"

}

Ожидается:

POST /api/user HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "birthdate": "1990-12-31"

}

Как проверить:

  1. Проверьте формат данных в документации API.

  2. Убедитесь, что сервер принимает отправленный формат.

Возможные статус-коды:

  • 400 Bad Request.

  • 422 Unprocessable Entity.

 

15. Атрибут имеет слишком длинное или короткое значение

Проблема: Длина значения атрибута выходит за допустимые границы.

Пример запроса: Клиент отправляет:

POST /api/comment HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "text": ""

}

Ожидается:

POST /api/comment HTTP/1.1

Host: example.com

Content-Type: application/json

{

    "text": "This is a valid comment."

}

Как проверить:

  1. Проверьте минимальные и максимальные ограничения длины для атрибута.

  2. Отправьте запрос с длиной значения в допустимых пределах.

Возможные статус-коды:

  • 400 Bad Request.

  • 422 Unprocessable Entity.

 

16. Проблема в кодировке данных

Проблема: Данные отправляются в неправильной кодировке (например, вместо UTF-8 используется ISO-8859-1).

Пример запроса: Клиент отправляет:

POST /api/submit HTTP/1.1

Host: example.com

Content-Type: text/plain; charset=ISO-8859-1

Ожидается:

POST /api/submit HTTP/1.1

Host: example.com

Content-Type: text/plain; charset=UTF-8

Как проверить:

  1. Проверьте заголовок Content-Type и кодировку данных.

  2. Убедитесь, что сервер поддерживает используемую кодировку.

Возможные статус-коды:

  • 400 Bad Request.

  • 500 Internal Server Error.
