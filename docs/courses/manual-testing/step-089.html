Лекция «HTTP-статус-коды 200: успешные сценарии»

 

Коды из группы 200 говорят о том, что запрос клиента был успешно обработан сервером. Эти коды — самые частые в работе тестировщика, поскольку они сигнализируют, что всё прошло как надо. Понимание их логики помогает уверенно работать с API.

 

Что это значит?

Коды 200 подтверждают, что сервер понял запрос клиента, выполнил его и вернул ожидаемый результат. Это успешное завершение взаимодействия. Такие коды используются в разных сценариях: от получения данных до создания нового ресурса или обновления существующего.

 

Основные коды 200 и как их получить

200 OK

Что это значит? Запрос успешно выполнен, и сервер возвращает данные. Это самый универсальный статус, который может использоваться практически для всех методов HTTP.

Как получить?

GET-запрос: Если ресурс существует и может быть возвращён сервером, вы получите 200 OK. Пример: GET /products HTTP/1.1

Host: example.com

Ответ: 200 OK

[

  { "id": 1, "name": "Laptop" },

  { "id": 2, "name": "Smartphone" }

]

POST-запрос: Иногда сервер возвращает 200 OK, даже если ресурс создан (вместо 201 Created), особенно если он возвращает полный объект ресурса.

Пример: POST /users HTTP/1.1

Host: example.com

Content-Type: application/json

{

  "name": "Alice",

  "email": "alice@example.com"

}

Ответ: 200 OK

{

  "id": 1,

  "name": "Alice",

  "email": "alice@example.com"

}

PATCH-запрос: Если частичное обновление ресурса прошло успешно, сервер может вернуть 200 OK вместе с обновлённым объектом.

Пример: PATCH /users/1 HTTP/1.1

Host: example.com

Content-Type: application/json

{

  "email": "new.email@example.com"

}

Ответ: 200 OK

{

  "id": 1,

  "name": "Alice",

  "email": "new.email@example.com"

}

 

201 Created

Что это значит? Запрос выполнен, и новый ресурс создан. Это стандартный ответ для метода POST, реже используется с PUT.

Как получить?

POST-запрос: Пример: POST /orders HTTP/1.1

Host: example.com

Content-Type: application/json

{

  "productId": 123,

  "quantity": 2

}

Ответ: 201 Created

Location: /orders/456

{

  "id": 456,

  "productId": 123,

  "quantity": 2

}

PUT-запрос: Если API поддерживает создание ресурса через PUT, вы получите 201 Created.

Пример: PUT /users/123 HTTP/1.1

Host: example.com

Content-Type: application/json

{

  "name": "Bob",

  "email": "bob@example.com"

}

Ответ: 201 Created

 

202 Accepted

Что это значит? Запрос принят, но обработка ещё не завершена. Это означает, что операция выполняется асинхронно, и результат будет доступен позже.

Как получить?

POST-запрос для долгих операций: Пример: POST /process HTTP/1.1

Host: example.com

Content-Type: application/json

{

  "task": "generate-report"

}

Ответ: 202 Accepted

{

  "message": "Your task is being processed",

  "taskId": "abc123"

}

 

204 No Content

Что это значит? Запрос успешно выполнен, но сервер не возвращает тело ответа. Это полезно, если клиенту достаточно подтверждения выполнения операции.

Как получить?

DELETE-запрос: Пример: DELETE /users/1 HTTP/1.1

Host: example.com

Ответ: 204 No Content

PUT-запрос: Если обновление данных прошло успешно, но возвращать обновлённый объект не требуется.

Пример: PUT /users/1 HTTP/1.1

Host: example.com

Content-Type: application/json

{

  "email": "updated.email@example.com"

}

Ответ: 204 No Content

 

Рекомендательный характер

Как и HTTP-методы, статус-коды носят рекомендательный характер. Сервер может возвращать, например, 200 OK вместо 201 Created, если его логика построена так, что создание ресурса не требует выделения отдельного кода.

  • Вы можете получить 200 OK вместо 204 No Content, если сервер возвращает текст подтверждения удаления.

  • То же самое касается кода 202 Accepted: его можно заменить на 200 OK, если сервер не использует асинхронную обработку.

 

Почему это нужно понимать?

Эти статус-коды — основа работы с API. Они подтверждают, что запросы выполнены успешно, и помогают интерпретировать ответ сервера. Понимание их логики необходимо, чтобы:

  • Проверять корректность выполнения запросов.

  • Понимать, что произошло на сервере.

  • Быть готовым к нестандартным реализациям API, где статус-коды могут отклоняться от рекомендаций.

Теперь, когда мы разобрались с успешными сценариями, можно перейти к кодам других групп, чтобы видеть полную картину работы с HTTP.

 

Ошибки использования

Статус 200 OK часто воспринимается как показатель успеха, но на практике может скрывать ошибки. Например:

Сервер возвращает 200 OK, но данные пустые: Это может быть связано с неправильной обработкой логики. Например, запрос: GET /products?category=nonexistent HTTP/1.1

Host: example.com

Ответ: 200 OK

[]

Технически это успех, но пустой массив может указывать на проблему с бизнес-логикой (например, категория существует, но сервер её не нашёл).

Ошибка внутри тела ответа: Сервер возвращает 200 OK, но в теле ответа — сообщение об ошибке: 200 OK

{

  "error": "Invalid query parameter"

}

Это нарушение стандартов и может запутать клиента.

Тестировщик должен проверять не только статус-код, но и содержимое ответа, заголовков, чтобы убедиться, что данные соответствуют ожиданиям.

 

Логика работы с пустыми ответами

Некоторые запросы могут возвращать статус-код 204 No Content, что может сбивать с толку. Это не ошибка, а решение серверной логики.

  • DELETE: Если удаление ресурса прошло успешно, сервер может вернуть 204 No Content, подтверждая выполнение операции.

  • PUT или PATCH: Если изменения применены, но клиенту не нужно видеть обновлённые данные, сервер тоже может вернуть 204 No Content.

Однако, если сервер возвращает 200 OK при выполнении таких операций, это может быть сигналом для проверки логики API.
