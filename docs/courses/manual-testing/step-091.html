Лекция «HTTP-статус-коды 400: клиентские ошибки»

 

Статус-коды группы 400 сигнализируют о том, что запрос клиента не может быть обработан из-за ошибки с его стороны. Такие коды являются ключевыми для тестировщиков, так как они помогают определить, где запрос был составлен неправильно, и в чём именно проблема.

 

Что это значит?

Коды 400 означают, что ошибка произошла на стороне клиента, а не сервера. Это может быть:

  • Некорректный формат данных.

  • Отсутствие необходимых параметров.

  • Ошибки авторизации или доступа.

  • Слишком частые запросы.

Важно понимать, что вы можете получить эти ошибки как из-за неисправности самого продукта, так и из-за некорректного запроса, созданного специально для проверки работы API. Ваша задача как тестировщика — не только интерпретировать эти ошибки, но и уметь сознательно их вызывать, чтобы проверить, что система работает так, как задумано.

Со стороны браузера такие ошибки сложнее воспроизводить без дополнительных инструментов. Именно поэтому для тестирования API используются специализированные инструменты, такие как Postman или Insomnia. С их помощью вы можете управлять запросами и вызывать ошибки, задавая неверные параметры или авторизационные данные.

 

Основные коды 400 и как их получить

400 Bad Request

Что это значит? Сервер не может обработать запрос из-за его некорректности. Это может быть некорректный синтаксис, отсутствие обязательных параметров или неправильный формат данных.

Как получить?

Отправьте запрос с некорректным синтаксисом: Пример:

GET /products?price=invalid HTTP/1.1

Host: example.com

Ответ: 400 Bad Request

{

  "error": "Invalid parameter: price"

}

Где это встречается?

  • Когда обязательные параметры отсутствуют.

  • Если данные имеют неверный формат (например, ожидается число, а передаётся текст).

 

401 Unauthorized

Что это значит? Клиент не предоставил правильные данные для авторизации, или доступ к ресурсу требует аутентификации.

Как получить?

Отправьте запрос без заголовка авторизации: Пример:

GET /users/me HTTP/1.1

Host: example.com

Ответ: 401 Unauthorized

{

  "error": "Authentication required"

}

Где это встречается?

  • При попытке получить доступ к защищённым ресурсам без токена авторизации.

  • Когда предоставленный токен недействителен или истёк.

 

403 Forbidden

Что это значит? Клиент аутентифицирован, но не имеет прав доступа к ресурсу. Это ошибка авторизации на уровне доступа.

Как получить?

Отправьте запрос с авторизацией, но к ресурсу, к которому у вас нет прав: Пример:

GET /admin/dashboard HTTP/1.1

Host: example.com

Authorization: Bearer valid_token

Ответ: 403 Forbidden

{

  "error": "You do not have permission to access this resource"

}

Где это встречается?

  • При попытке доступа к ресурсам, требующим административных прав.

  • Когда пользователь имеет ограничения по ролям.

 

404 Not Found

Что это значит? Сервер не может найти запрашиваемый ресурс. Это может быть связано с неправильным URL или отсутствием ресурса на сервере.

Как получить?

Отправьте запрос на несуществующий ресурс: Пример:

GET /nonexistent-path HTTP/1.1

Host: example.com

Ответ: 404 Not Found

{

  "error": "Resource not found"

}

Где это встречается?

  • Когда клиент использует неправильный путь или идентификатор.

  • Если ресурс был удалён.

 

429 Too Many Requests

Что это значит? Клиент отправил слишком много запросов за короткий промежуток времени, и сервер временно блокирует дальнейшие запросы.

Как получить?

Отправьте несколько запросов подряд за короткий промежуток времени: Пример:

GET /products HTTP/1.1

Host: example.com

Ответ: 429 Too Many Requests

{

  "error": "Rate limit exceeded. Try again later."

}

Где это встречается?

  • При настройке лимитов запросов на стороне сервера (rate limiting), что ограничивает количество запросов за определённый период.

  • Когда клиент злоупотребляет API.

 

422 Unprocessable Entity

Что это значит?

Код 422 сигнализирует, что сервер понял запрос, но не может его обработать из-за некорректных данных, которые не соответствуют валидации или бизнес-логике.

Пример для POST: Если клиент отправляет запрос с неправильной структурой JSON:

POST /users HTTP/1.1  

Host: example.com  

Content-Type: application/json  

{  

  "name": "Alice",  

  "email": "not-an-email"  

}

Ответ:

HTTP/1.1 422 Unprocessable Entity  

Content-Type: application/json  

{  

  "error": "Invalid email format"  

}

Где это встречается?

  • Если сервер не может обработать данные, потому что они не прошли валидацию.

  • Если JSON имеет правильный синтаксис, но его содержимое некорректное (например, email невалидный).

  • Если переданы обязательные поля, но с недопустимыми значениями.

 

Связь с 400 Bad Request

Код 422 — это ранний вариант 400 Bad Request. Раньше его использовали для случаев, когда запрос технически правильный, но сервер не может его обработать. Сейчас 400 используется как стандарт, но 422 всё ещё встречается в некоторых API.

Если видите 422, воспринимайте его так же, как 400 Bad Request.

 

Рекомендательный характер

Коды группы 400 — это стандартные рекомендации, но серверы могут обрабатывать клиентские ошибки по-разному:

  • Сервер может вернуть 400 Bad Request, даже если отсутствует токен авторизации, вместо 401 Unauthorized.

  • 404 Not Found может возвращаться вместо 403 Forbidden в случае, если доступ к ресурсу не разрешён и нужно скрыть его существование.

  • Коды, связанные с лимитами, могут варьироваться в зависимости от политики сервера.

 

Почему это нужно понимать?

Эти коды важны, потому что они помогают тестировщику:

  • Выявлять ошибки в запросах клиента.

  • Понимать, как API обрабатывает некорректные запросы.

  • Проверять, правильно ли настроена система авторизации и доступа.

  • Тестировать работу ограничений, таких как лимиты запросов.

Помимо того, что такие ошибки могут указывать на проблемы в продукте, тестировщик должен уметь сознательно вызывать их, чтобы проверить, что они возвращаются корректно. Используйте инструменты, такие как Postman или Insomnia, чтобы управлять параметрами запросов и анализировать ответы сервера. Это поможет вам не только находить проблемы, но и уверенно объяснять их разработчикам.
