Лекция «Как тестировать бэкенд?»

 

Бэкенд отвечает за обработку логики и данных. В отличие от фронтенда, тестирование бэкенда требует работы с API, базы данных и проверки бизнес-логики.

Для полноценного тестирования бэкенда важно собрать как можно больше информации из требований, от разработчика или интервьюера, если вы на собеседовании. Используя приведенные ниже материал, вы сможете найти нужные данные и задать правильные вопросы. С этой информацией можно приступать к тестированию, обеспечив более точные и эффективные результаты.

Для успешного тестирования необходимо выяснить следующие моменты:

  1. URL и эндпоинт

  2. Какие квери параметры

  3. Формат сообщения (JSON, XML и т.д.)

  4. Какое заголовок/тело запроса

    1. Количество атрибутов

    2. Название атрибутов

    3. Тип данных

    4. Обязательные и не обязательные

    5. Классы эквивалентности

    6. Ограничения

      1. На длину/дату/время

      2. Доступности роли

  5. Какое тело ответа

    1. Успешный результат

    2. Неуспешный результат

      1. Не тот метод (ожидаем А, отправляем Б) - 405

      2. Пустое тело - 400

      3. Отсутствуют обязательные поля - 400

      4. Пустые обязательные поля "" - 400

      5. null обязательные поля - 400

      6. Неверный тип данных - 400

      7. Превышены ограничения - 400

      8. Отсутствуют права - 403

      9. Отсутствует авторизация - 401

      10. Нельзя выполнить процесс, т.к. он занят (Процесс стоит на этапе сборки товара, а мы пытаемся еще раз оплатить). - 409

      11. Сущность не существует - 404

      12. Текст ошибки соответствует и понятный ошибке то что описано выше

      13. При этом всем проверка на соответствие статус кода по этим ошибкам (400, 401, 403, 404, 405, 409)

      14. Недоступный сервер - 500, 503, 504

  6. Что происходит с сущностью в БД при её создании, обновлении или удалении

  7. Дублируется ли или создастся новое, что предусмотрено логикой API

  8. Ограничения на количество запросов за определенное время, как с одного IP или как с одного устройства

 

ЭТО ВСЁ ВЫУЧИТЬ НА ЗУБОК. ОТ 1 ДО 8. Прям всё? Да, всё. 

Не всё проверяется на работе, потому что не все методы можно протестировать таким образом из-за особенностей их реализации

 

Что тестируем на бэкенде?

  • API → Отвечает ли сервер на запросы? Корректно ли возвращает данные?

  • База данных → Сохраняются ли данные правильно? Нет ли потерь?

  • Бизнес-логика → Выполняются ли расчёты, проверки, условия?

  • Безопасность → Можно ли получить данные без авторизации?

  • Ошибки → Как API обрабатывает некорректные запросы?

 

Как тестировать API?

Для тестирования API используются Postman, Swagger и другие инструменты, которые позволяют отправлять запросы и анализировать ответы.

Основные проверки:

  • Ответы сервера → Кода 200, 400, 500

  • Структура данных → Совпадает ли с документацией? Количество и название

  • Граничные значения → Что будет, если передать неверные или слишком большие данные?

  • Безопасность → Можно ли получить данные без токена или с чужими правами?

 

Создание товара: пример тестирования

Создание выполняется через POST-запрос.

Что важно:

  • URL → /api/products

  • Метод → POST

  • Заголовки → Content-Type: application/json, Authorization: Bearer <токен>

  • Тело запроса:

{

  "name": "Смартфон",

  "price": 999,

  "category": "Электроника",

  "stock": 10

}

 

Что проверяем?

  • Успешное создание → Код 200 ОК или 201 Created, API возвращает id товара, в нашем случае, но не обязательно.

  • Данные в базе → Проверяем, что товар появился. Если нет доступа к БД, вытаскиваем через GET-запрос.

  • Обязательные поля → Убираем как по 1 так и массово name, price, category, ожидаем 400 Bad Request. Смотри как реагирует ли только на первое поле или на все. Если только на одном, придется проверять по одному полю, если сразу на всё. То сэкономите время

  • Обработка ошибок → Если передаём price: "100" (в виде строки), сервер должен вернуть ошибку. 400 Bad Request.

 

Что тестируем в теле запроса?

  • Какие атрибуты передаются → Название, структура, количество.

  • Типы данных → Строка, число, массив и т. д.

  • Все заполненные поля → убедиться, что система работает

  • Обязательные и необязательные поля → Какие можно опустить? Убедиться, что необязательные поля действительно необязательные и обязательные действительно обязательные.

  • Границы значений → Минимальные, максимальные значения и +-1 от границы

  • Пустые значения → name: null или name: “”→ API должно реагировать и выдавать ошибку, если обязательное поле.

  • Пустое тело →  тело без всех полей, но должно сохранять формат данных, например JSON {}, 

  • Неверный тип данных → price: "100" → API должно вернуть ошибку, т.к. это строка.

Изменение типа данных В большинстве случаев это не нужно проверять, так как с этим редко бывают проблемы. Но для своего спокойствия — можно протестировать.

 

Что тестируем в заголовках запроса?

1. Content-Type → Соответствует ли передаваемым данным?

  • Если указано Content-Type: application/json, но тело запроса не JSON, сервер должен вернуть 415 Unsupported Media Type.

  • Если Content-Type отсутствует, API может либо проигнорировать его, либо вернуть ошибку.

Некоторые API требуют аутентификацию.

2. Authorization → Работает ли аутентификация?

  • Без токена → Ожидаем 401 Unauthorized.

  • С неверным токеном → Ожидаем 401 Unauthorized.

  • С правильным токеном, но недостаточными правами → Ожидаем 403 Forbidden.

  • Время жизни токена → Проверяем, как сервер реагирует на истёкший токен (должен вернуть 401 Unauthorized).

  • Запрос с правильным токеном, но недостаточными правами → Ожидаем 403 Forbidden.

Стандартные заголовки (Host, User-Agent, Accept, Referer) обычно не тестируются, если нет специфических требований. Но если API использует кастомные заголовки (X-Correlation-ID, X-Request-ID), их тестирование проводится согласно требованиям, проверяя, как сервер обрабатывает их наличие, отсутствие или некорректные значения.

 

Обновление данных (PUT vs PATCH)

PUT — заменяет весь объект, требует передачу всех полей. PATCH — обновляет только переданные поля.

Пример PATCH:

{

  "price": 899

}

Что проверяем?

  • PUT → Удаляет ли не переданные поля?

  • PATCH → Сохраняет ли старые данные?

  • Валидация → Можно ли отправить пустые поля?

 

Удаление товара

Удаление выполняется методом DELETE.

Что проверяем?

  • Успешное удаление → 200 OK или 204 No Content.

  • Повторное удаление → 404 Not Found.

  • Можно ли удалить товар, если он уже используется? Если да — баг.

 

Разные роли пользователей

Проверяем:

  • Администратор → Может создавать, обновлять, удалять товары.

  • Пользователь → Может только просматривать.

  • Гость → Не должен видеть закрытые товары.

Если нет прав → 403 Forbidden.

 

Ошибки и обработка исключений

API должно правильно обрабатывать ошибки:

  • 400 Bad Request — неверные данные.

  • 401 Unauthorized — нет авторизации.

  • 403 Forbidden — нет прав.

  • 404 Not Found — ресурс не найден.

  • 409 Conflict — конфликт (например, товар уже существует).

  • 500 Internal Server Error — сервер сломался (и этого быть не должно).

 

Итог

Тестирование бэкенда — это проверка API, структуры данных, базы и авторизации.

  1. Проверяем, что запрос отправляется правильно → Метод, URL, заголовки, тело.

  2. Проверяем, что сервер отвечает корректно → Код ответа, структура данных.

  3. Проверяем, что данные сохраняются в БД → Если доступа к БД нет, смотрим через GET-запрос.

  4. Тестируем ошибки → Отсутствие полей, неверные значения, токены.

Без требований тестирование бэкенда превращается в угадайку. Запросите у разработчиков примеры запросов и ожидаемые результаты. Это упростит тестирование и поможет избежать бессмысленной работы.

Это практически всё, что вам нужно знать для успешного прохождения собеседований и работы, остальное специфичное и изучите на месте.

 

 

 

Что нужно уметь рассказать
– Что именно тестируем: API, база данных, бизнес-логика, безопасность, ошибки
– Как тестируем API: метод, URL, заголовки, тело, структура ответа
– Проверка обязательных и необязательных полей
– Проверка типов данных и граничных значений
– GET/POST могут использоваться для поиска данных
– POST используется для создания и иногда обновления
– PUT/PATCH — обновление (PUT полностью заменяет, PATCH частично меняет поля)
– DELETE — удаление ресурса (физическое или логическое)
– Обработка ошибок (400, 401, 403, 404, 405, 409, 500, 503, 504)
– Проверка разных ролей пользователей (админ, пользователь, гость)
