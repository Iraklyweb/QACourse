Лекция «Заголовки запроса в API»

Сети · REST

Когда клиент и сервер обмениваются данными через API, они используют заголовки запроса для передачи дополнительной информации. Заголовки помогают клиенту и серверу "понимать" друг друга: какой формат данных используется, кто отправляет запрос, какие права доступа у клиента и как обрабатывать данные.

Знание и правильное использование заголовков — ключ к успешной работе с API, особенно для тестировщиков.

Как формируются заголовки?

Заголовки представляют собой пары ключ: значение, которые передаются в HTTP-запросе или ответе.

Формат заголовков:

Заголовок: значение

Пример заголовков в HTTP-запросе:

POST /api/users HTTP/1.1  

Host: example.com  

Authorization: Bearer abc123token  

Content-Type: application/json  

Accept: application/json  

User-Agent: PostmanRuntime/7.29.2  

Здесь заголовки указывают, кто отправляет запрос, какие данные передаются и в каком формате клиент хочет получить ответ.

Пример заголовков в HTTP-ответе сервера:

HTTP/1.1 200 OK  

Content-Type: application/json  

Set-Cookie: sessionId=xyz456; Path=/; Secure; HttpOnly  

Cache-Control: no-cache  

Ответ содержит информацию о возвращаемых данных, управлении сессиями и кэшировании. Формирование и отправка заголовков зависит от клиента. В обычных условиях их автоматически устанавливает браузер, мобильное приложение или другой клиент, если это предусмотрено разработчиком. При тестировании API заголовки можно изменять и настраивать вручную с помощью специальных инструментов. Некоторые заголовки вам придётся формировать самостоятельно в соответствии с требованиями системы.

Где увидеть заголовки запроса и ответа?

Заголовки можно посмотреть в инструментах для работы с API:

  • В браузере (DevTools → вкладка "Сеть")

  • В Postman (раздел Headers)

  • В терминале (cURL, например curl -v)

Пример вывода заголовков через curl:

curl -v -H "Authorization: Bearer abc123token" https://example.com/api/users

В ответе можно увидеть заголовки сервера и понять, какие данные он возвращает.

Как понять, что заголовки правильные?

Проверка заголовков важна при тестировании API. Ошибки в заголовках могут приводить к сбоям в работе сервиса.

На что обращать внимание:

  • Заголовки должны соответствовать спецификации API — API может требовать обязательные заголовки, без которых запрос не будет обработан.

  • Формат заголовков должен быть корректным — Content-Type должен совпадать с передаваемыми данными.

  • Правильность значений — передаваемый токен должен быть валидным, а заголовки, связанные с сессиями, должны соответствовать требованиям сервера.

  • Реакция сервера на некорректные заголовки — например, если передать неверный Content-Type, сервер должен вернуть 415 Unsupported Media Type.

Группы заголовков

Авторизация и безопасность

Используются для подтверждения личности клиента и защиты данных.

Authorization — передаёт данные для аутентификации (например, токен доступа).

Токен — это уникальная строка, которая подтверждает, что у пользователя есть права на доступ к системе. Он работает как электронный ключ: сервер выдаёт его после успешного входа, а затем клиент использует токен в каждом запросе вместо логина и пароля.

На тестировании проверяется, что:

  • Запрос без токена возвращает 401 Unauthorized.

  • Запрос с неправильным токеном отклоняется и возвращается 401 Unauthorized.

  • Запрос с валидным токеном проходит.

Что такое Bearer-токен?

Bearer-токен — это тип токена, который клиент передаёт серверу в заголовке Authorization. Он используется для аутентификации и подтверждения прав доступа.

Пример использования:

Authorization: Bearer abc123token

Слово Bearer означает, что тот, кто предъявляет этот токен, считается авторизованным. Сервер не проверяет, кто отправил токен — если он валидный, доступ будет предоставлен.

Что тестировать?

  • Запрос без Bearer-токена должен возвращать 401 Unauthorized.

  • Запрос с истёкшим или поддельным токеном тоже должен возвращать 401 Unauthorized.

  • Если токен корректный, сервер должен разрешить выполнение запроса.

Что такое JWT (JSON Web Token)?

JWT — это формат Bearer-токена, который представляет собой зашифрованную строку, содержащую данные о пользователе и его правах.

Пример JWT-токена:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOjEsInJvbGUiOiJhZG1pbiIsImlhdCI6MTY5MDAwMDAwMCwiZXhwIjoxNjkwMDkwMDAwfQ.TJVA95OrM7E2cBab30RMHrHDcEfxjoYZgeFONFh7HgQ

Он состоит из трёх частей, разделённых точками:

  1. Заголовок (Header) — содержит информацию о типе токена и алгоритме шифрования.

  2. Полезная нагрузка (Payload) — включает данные о пользователе, его роли и сроке действия токена.

  3. Подпись (Signature) — используется для проверки подлинности токена.

Что тестировать?

  • Декодирование токена — убедиться, что в Payload не хранятся чувствительные данные (например, пароли).

  • Срок действия (exp) — если токен истёк, сервер должен вернуть 401 Unauthorized.

  • Роли (role) — у пользователя должны быть правильные права доступа.

Cookie

Cookie — передаёт данные о сессии клиента. Пример:

Cookie: sessionId=xyz456

Идентификатор — это уникальный код или строка, с помощью которой система отличает один объект от другого. В случае сессии он нужен, чтобы понять, какой пользователь выполняет запрос.

Сессия — это период активности пользователя на сайте или в приложении. Пока сессия активна, сервер "помнит" пользователя, его данные и настройки, чтобы не запрашивать их каждый раз заново.

Cookie с идентификатором сессии позволяет серверу понимать, кто отправляет запрос, и связывать его с текущим состоянием пользователя. Это нужно, например, чтобы не заставлять пользователя логиниться заново при каждом переходе на новую страницу.

Проверяется, что:

  • Запрос без корректного Cookie приводит к разрыву сессии.

  • Сервер корректно обрабатывает запросы с переданным Cookie.

  • При истечении срока действия Cookie сервер требует новую аутентификацию.

Формат данных

Определяют, в каком формате клиент передаёт и принимает данные.

Content-Type — указывает формат передаваемых данных. Пример:

Content-Type: application/json

На тестировании проверяется, что:

  • Передаваемый формат совпадает с фактическими данными.

  • Сервер корректно реагирует на неверный формат (415 Unsupported Media Type).

Accept — указывает, в каком формате клиент хочет получить ответ. Пример:

Accept: application/json

На тестировании проверяется, что:

  • Сервер возвращает данные в нужном формате.

  • Если запрашиваемый формат недоступен, сервер выдаёт 406 Not Acceptable.

Сведения о клиенте

Передают информацию о том, откуда пришёл запрос.

User-Agent — передаёт данные о клиенте (браузер, скрипт, Postman). Пример:

User-Agent: PostmanRuntime/7.29.2

Используется в тестировании, если система блокирует определённые User-Agent или требует их наличия.

Referer — указывает, с какого ресурса пришёл запрос. Пример:

Referer: https://example.com/

Позволяет отслеживать, откуда пришёл запрос. Может использоваться для защиты от подделки запросов (CSRF).

Host — указывает, к какому серверу направляется запрос. Пример:

Host: example.com

Если на одном IP-адресе работает несколько сайтов или сервисов, заголовок Host сообщает серверу, к какому из них относится запрос. Браузер автоматически добавляет этот заголовок. Если же запрос отправляется напрямую без Host, сервер ответит в зависимости от его настройки — либо вернёт страницу по умолчанию, либо ошибку.

Кэширование и оптимизация

Заголовки, которые управляют хранением данных и настройками соединения.

  • Cache-Control: указывает, как сервер должен кэшировать данные.

  • Accept-Encoding: указывает, какие методы сжатия данных поддерживает клиент.

Какие заголовки тестирует тестировщик?

Хотя заголовков запроса существует множество, в реальной работе тестировщика вы чаще всего будете работать с:

  • Authorization — работа авторизации, корректность токенов.

  • Cookie — обработка сессий и авторизации.

  • User-Agent — в случаях, когда важно, откуда приходит запрос.

Итог

Заголовки запроса и ответа передают важную информацию о данных, авторизации и работе API.

Понимание этих заголовков помогает находить ошибки и тестировать API более эффективно.
