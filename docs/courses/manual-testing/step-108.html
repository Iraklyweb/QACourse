Лекция «Как тестировать API: основные подходы и сценарии»

 

API тестируется на основе требований, которые описывают, как система должна работать. Если требования неясны или отсутствуют, важно уточнить детали у разработчиков, бизнес-аналитиков или заказчика. Только при чётком понимании ожиданий можно грамотно составить сценарии тестирования.

 

1. Тестирование заголовков

Контекст: Заголовки — это ключевая часть запросов, которая определяет, как сервер обрабатывает данные. Некоторые заголовки обязательны (например, Authorization), и их отсутствие может сделать запрос недействительным. В других случаях заголовки влияют на дополнительные параметры работы API (например, кэширование или тип данных).

Цель: Проверить, как сервер обрабатывает корректные и некорректные заголовки.

  • Удаление заголовков: Если заголовок X обязателен, убедитесь, что его отсутствие приводит к ожидаемой ошибке (например, 400 Bad Request или 401 Unauthorized).

  • Пустой заголовок: Проверьте, как сервер реагирует, если обязательный заголовок X отправляется без значения.

  • Неверное значение заголовка: Если заголовок X должен содержать Y, отправьте значение Z и проверьте, возвращает ли сервер корректную ошибку (например, 403 Forbidden или 400 Bad Request).

  • Авторизация: Заголовок авторизации (Authorization) обязателен для защищённых ресурсов.

    1. Отправьте запрос без токена — сервер должен вернуть 401 Unauthorized.

    2. Попробуйте использовать токен с недостаточными правами (другая роль) — сервер должен вернуть 403 Forbidden.

 

2. Тестирование тела запроса

Контекст: Тело запроса используется для передачи данных серверу. Например, при создании ресурса или его обновлении. Некоторые поля могут быть обязательными, и их отсутствие делает запрос недействительным. Другие поля могут быть необязательными, и сервер должен корректно их игнорировать или обрабатывать.

Цель: Проверить, как сервер обрабатывает корректные и некорректные данные в теле запроса.

  • Пустое тело: Если тело запроса обязательно (например, для POST или PUT), в этом случае сервер должен вернуть (400 Bad Request).

  • Только обязательные поля: Проверьте, что запрос с минимальным набором данных обрабатывается успешно.

  • Все поля: Убедитесь, что сервер принимает запрос с обязательными и необязательными полями. Необязательные поля должны либо игнорироваться, либо обрабатываться в соответствии с требованиями.

  • Удаление обязательных полей: Проверьте, как сервер реагирует, если удалить одно или несколько обязательных полей. Например:

    • Удалили одно поле — получили 400 Bad Request.

    • Удалили несколько полей — ошибка должна быть аналогичной или содержать указание на все отсутствующие поля.

  • Очистка значений обязательных полей: Если значение поля должно быть не пустым, отправьте запрос с пустым значением и проверьте, что сервер вернёт корректную ошибку.

  • Некорректный тип данных: Если поле ожидает число, отправьте строку или объект. Сервер должен отклонить запрос (400 Bad Request).

  • Граничные значения: Проверьте минимальные, максимальные и пограничные значения. Например, если длина имени должна быть от 3 до 50 символов:

    • Отправьте запрос с именем из 2 символов — ошибка.

    • Отправьте запрос с именем из 51 символа — ошибка.

    • Отправьте запрос с 3 или 50 символами — успешный ответ.

  • Логика переходов: Убедитесь, что сервер корректно обрабатывает переходы состояний (например, от "активного" к "завершённому").

 

3. Логика и соответствие требованиям

Контекст: Тестирование логики — это проверка соответствия API функциональным требованиям. Вы должны убедиться, что ответы сервера, изменение данных и выполнение операций соответствуют описанным ожиданиям.

Цель: Проверить, как сервер выполняет операции в зависимости от переданных данных.

  • Проверка ответа: Если запрос содержит данные X, убедитесь, что в ответе возвращаются соответствующие данные.

  • Проверка метода: Убедитесь, что сервер принимает только те методы, которые указаны в документации (например, POST для создания, но не GET).

  • Сохранение данных в БД: После выполнения запроса убедитесь, что данные корректно сохранились в базе. Например:

    • Создали запись — данные есть в БД.

    • Удалили запись — данные отсутствуют в БД.

 

4. Тестирование методов API

DELETE

  • Что проверять: Удаление ресурса должно:

    1. Удалить данные из базы.

    2. Возвращать корректный статус-код (204 No Content или 200 OK).

    3. Обрабатывать случай, если ресурс уже удалён (404 Not Found).

PATCH

  • Что проверять: Изменение ресурса должно:

    1. Затрагивать только указанные поля.

    2. Сохранять остальные поля без изменений.

    3. Возвращать обновлённые данные (если это предусмотрено).

PUT

  • Что проверять: Полное обновление ресурса должно:

    1. Заменять все данные сущности.

    2. Создавать новый ресурс, если он отсутствует (если это предусмотрено логикой).

GET

  • Что проверять: Запрос данных должен:

    1. Возвращать корректный результат для существующего ресурса.

    2. Возвращать 404 Not Found для отсутствующего ресурса.

    3. Соответствовать данным в базе.

POST

  • Что проверять: Создание ресурса должно:

    1. Добавлять новые данные в систему.

    2. Возвращать корректный статус-код (201 Created или 200 OK, если предусмотрено).

    3. Генерировать уникальный идентификатор для нового ресурса (если это требуется).

    4. Обрабатывать случаи, когда переданы некорректные или неполные данные (400 Bad Request).

    5. Исключать дублирование записей (если система этого требует).

 

Итог

Тестирование API включает проверку заголовков, тела запроса, методов и логики работы. Основные моменты:

  1. Тестируйте на основе требований — это основа для правильного анализа. Если требований нет, уточняйте их.

  2. Проверяйте корректность обязательных данных — их отсутствие или неверный формат должен корректно обрабатываться системой.

  3. Убедитесь, что изменения в API (создание, удаление, обновление) корректно отражаются в базе данных и системе в целом.

Этот подход позволяет структурировать работу и максимально охватить все ключевые сценарии.
