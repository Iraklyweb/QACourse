Лекция «Как сдавать ДЗ по POSTMAN»

SQL · Практика

Почему раньше не было сказано, как необходимо сдавать ДЗ? Мы решили дать вам возможность самим подумать и придумать, как бы вы хотели организовать процесс. Это было сделано, чтобы вы могли сами прийти к оптимальному решению. Сейчас же мы выбрали универсальный подход, который зарекомендовал себя как наиболее эффективный.

Сдача ДЗ по POSTMAN должна быть похожа на коллекцию приведенную ниже.

https://drive.google.com/file/d/14Mmc_qro3SSzcuHR7VplwNAQ-H58rxke/view?usp=sharing

Подробная структура коллекции в Postman

1. Задание Создать питомца

  • Главная папка, в которой хранится вся информация и сценарии по созданию питомца через API.

  • Папка названа согласно выполняемому заданию.

2. Основной сценарий

  • Содержит основной, стандартный сценарий создания питомца, который должен проходить успешно и возвращать корректный результат.

  • Внутри него хранится запрос POST («Создать питомца»), содержащий обязательные и опциональные поля, которые должны быть заполнены согласно требованиям.

3. Альтернативный сценарий

  • Включает сценарий, который отличается от основного, но также считается валидным.

  • Этот запрос позволяет проверить работу API при отличных от стандартных условиях, например, отправка данных в другом формате или с другими комбинациями полей.

4. Обязательность полей

  • Внутри содержатся запросы, проверяющие API на корректную обработку ситуации, когда обязательные поля не заполнены.

  • Каждый запрос представляет собой проверку одного уровня обязательных полей:

    • POST Без 1 уровня – проверка обязательности полей первого уровня вложенности.

    • POST Без 2 уровня – проверка обязательности вложенных полей второго уровня.

    • POST Без 3 уровня – проверка более глубокого уровня обязательных полей вложенности.

5. Опциональность полей

  • Запросы для проверки корректной обработки API в ситуации, когда не заполняются необязательные (опциональные) поля:

    • POST Без 1 уровня – проверяет, что API корректно обрабатывает отсутствие необязательных полей первого уровня.

    • POST Без 2 уровня – аналогично для полей второго уровня вложенности.

6. Min/Max (Минимальные и максимальные значения)

  • Содержит запросы, проверяющие API на корректность обработки минимально и максимально допустимых значений полей:

    • POST min – отправляет данные с минимальными допустимыми значениями, проверяется нижняя граница.

    • POST max – отправляет данные с максимально допустимыми значениями, проверяется верхняя граница.

7. Невалидные запросы

  • Группа запросов, проверяющих негативные сценарии:

    • POST min -1 – отправка значений ниже допустимых минимальных значений.

    • POST max +1 – отправка значений выше допустимых максимальных значений.

    • POST Не справочное значение – отправка некорректного (неизвестного) значения, не соответствующего справочнику.

    • POST Без заголовка Y – проверка обработки запроса без обязательного заголовка Y.

    • POST Без заголовка X – аналогичная проверка другого обязательного заголовка X.

    • POST Заголовок N = V – отправка запроса с некорректным значением заголовка N.

    • POST Протухший токен – отправка запроса с невалидным, устаревшим токеном авторизации.

    • POST Без токена – проверка обработки ситуации, когда отсутствует обязательный токен авторизации.

Эта структура помогает максимально систематизировать и упорядочить тестирование API, чтобы быстро и удобно проводить проверки всех возможных сценариев и пограничных ситуаций.
